# Agent Instructions

Instructions for AI coding agents working in this repository.

## Repository overview

This repository is the **Agentic Business Platform Accelerator for SAP on AWS**. It has three parts:

- An Amazon Bedrock AgentCore enterprise platform: Runtime, Gateway, Identity, Memory,
  observability and security controls. It is deployed with the AWS Cloud Development Kit
  (CDK) in Python.
- An SAP layer (`layers/sap/`).
- The business process agents that run on them, as use cases, one folder each under
  `use-cases/<name>/`.

The use cases in this checkout that have their own pages:

<!-- use-cases:begin -->
- [SAP exception handling](use-cases/business-operations/README.md) (`business-operations`): Business process agents for SAP exception handling, on the shared platform's Gateway, Cedar engine and interceptor.
- [Claude Code and Cowork on Amazon Bedrock](use-cases/claude-3p-on-bedrock/README.md) (`claude-3p-on-bedrock`): Claude Code and Claude Desktop/Cowork on Amazon Bedrock through Anthropic's Claude apps gateway, with Microsoft Entra ID sign-in and per-team model access, on the platform's private network.
- [hello-sap](use-cases/hello-sap/walkthrough.md) (`hello-sap`): Reference SAP use case — reads SAP through the SAP layer as its own Gateway client, and writes nothing.
<!-- use-cases:end -->

The platform works on its own. A use case runs on the platform and shares it with other use
cases (see [Rules for sharing the platform](#rules-for-sharing-the-platform)).

Before you make a change, decide whether it belongs to the platform (core) or to a use case.

## One dispatcher

One entry point keeps every command, its options and the configuration it reads in one
place. A person, CI and a coding agent then all run the same commands.

- `scripts/deploy.sh` is the only entry point: `doctor`, `design`, `build` (same as
  `deploy`), `verify`, `synth`, `diff`, `destroy`, `workshop`, `export`, `ls`, `config`,
  `migrate`, `usecase new|add|remove|list|run` and `layer run`. The comment at the top of `scripts/deploy.sh`
  gives the options of each one. It needs bash 4 or newer (macOS ships 3.2).
- A use case's operator commands are in its `ops.py`. They run as
  `scripts/deploy.sh usecase run <name> <verb>`.
- Never add a second dispatcher: no new Makefile targets, npm scripts or shell wrappers
  that fan out across the repo. The root `Makefile` comes from the upstream platform;
  leave it as it is and do not add to it.
- `platform.yaml` is the one deployment configuration. It is gitignored, and `deploy.sh design`
  writes it from a preset. Its reference, `docs/PLATFORM_YAML.md`, is generated by
  `scripts/gen_platform_reference.py`. Never edit the reference by hand.
- Deploying needs AWS credentials, Amazon Bedrock model access and the human's confirmation.
  Never deploy, destroy or change shared AWS resources unless asked to.

## Conventions

- CDK is Python, on Python 3.13. There is no TypeScript CDK.
- Core edits are additive and small. From a use case, attach to a platform resource by its
  id instead of editing a platform stack. The platform publishes these ids in SSM. The
  interface is `docs/PLATFORM_INTERFACE.md`, and the contract for a use case is
  `CONTRIBUTING_USE_CASES.md`.
- Never set a fixed physical resource name. Let CDK generate it, or build it from the
  deployment's names. A use case can build every name with `sap_kit/names.py`, which checks
  service limits when CDK synthesizes the templates (synth).
- Config refers to a secret by its Secrets Manager name, never by value. An operator
  command reads a secret from the terminal, never from its arguments.
- Headings, page titles, link text and diagram titles are technical labels: a noun phrase
  ("Architecture", "Prerequisites", "Case lifecycle"). No colon subtitles ("Architecture: what
  talks to what"), no questions, no conversational or second-person titles ("What it is",
  "Where to go next", "Your first case"). Renaming a linked heading means updating every
  anchor that points to it.
- Commit messages follow Conventional Commits.

## Rules for sharing the platform

Use cases share the Gateway, its policy engine, its interceptor and the user pool. A change
made for one use case can therefore affect every other use case. Three rules keep the
platform usable by any use case:

1. **The platform works with any use case turned off.** Removing a use case from
   `platform.yaml` leaves a platform that synthesizes, deploys and passes
   `deploy.sh verify`. Each use case checks this rule in its own tests or fixtures. Its
   `AGENTS.md`, where it has one, says where.
2. **Core changes are generic extension points.** No use-case, SAP or pack names in
   `stacks/`, `infra_utils/`, `app.py`, `scripts/` or `docs/`. Only `docs/start/`, the
   product's entry, may name SAP. A platform page names a use case, or links into its folder,
   only inside the blocks that `scripts/gen_use_case_index.py` writes from each use case's
   `manifest.yaml`. A core change must make sense to any use case.
3. **Shared controls touch only the owning use case's resources.** Interceptor checks and
   Cedar statements match that use case's target-prefixed tool names, never bare tool
   names. The names of groups, scopes and clients start with the use-case prefix. A setting
   that changes behaviour for every use case is a platform setting.

Cedar is off by default (`security.cedar.enabled`). When it is turned on, its mode is
`LOG_ONLY` by default. In both cases Cedar refuses nothing. A client that the Gateway accepts
can then call any tool that has no protection other than Cedar. `deployment.mode: production`
requires `ENFORCE`. A use case lists the risks that remain for it in its own threat model,
which its `AGENTS.md` names.

## Tests and checks

Run what covers your change before calling it done.

| What | Command |
|------|---------|
| Python suite | `python -m pytest -q -n auto`. `pytest.ini` limits it to `tests/` and to the fork's own tests next to the code they test: `use-cases/*/tests/`, `layers/*/tests/` and `sap_kit/tests/`. The `scripts/test_*.py` files are live smoke scripts, not tests. A test that synthesizes `app.py` goes through `tests/app_synth.py`, which synthesizes each configuration once per session |
| Synth parity | `scripts/check-contract.sh` (needs no AWS credentials) |
| CDK synth | `CDK_DEFAULT_ACCOUNT=111111111111 CDK_DEFAULT_REGION=us-east-1 npx cdk synth --app "python3 -B app.py" --quiet` |
| Docs and structure | `python scripts/check_docs.py`, `python scripts/check_repository_structure.py`, `python scripts/gen_platform_reference.py --check`, `python scripts/gen_use_case_index.py --check`, `python scripts/gen_posture_tiers.py --check` |
| Shell | `shellcheck --severity=warning $(git ls-files '*.sh')`, `bash scripts/check-deploy-config.sh`, `bash scripts/check-workshop-flow.sh` (bash 4+) |
| Control library | `python scripts/validate_control_library.py` |
| Lint | `ruff check` and `ruff format --check` |
| Security | `scripts/check-security.sh` runs the same scans as CI's security jobs: ASH (Automated Security Helper) over the source and over the synthesized templates of the production fixtures, the cdk-nag AwsSolutions pack over the same templates, and gitleaks over history. `source`, `templates`, `cdk-nag` or `gitleaks` runs one of them. It needs `ash`, `grype`, `syft`, `gitleaks`, and `cdk-nag` in `.venv`. Classify a finding before you suppress it in `.ash.yaml` or `.cdk-nag.yaml`. The header of each file gives the rule |
| Live | `scripts/deploy.sh verify` (needs a deployed stack). It runs the `verify.py` of each enabled use case last |

A use case's `verify.py` must be able to fail. It prints `OK: ...` and exits 0, or it prints
`FAIL: <cause>` and exits 1. It never ends in a traceback. The checks for each use case are
in that use case's `AGENTS.md`.

## Do not modify, or modify only deliberately

- Generated files, such as `docs/PLATFORM_YAML.md`: change the source and regenerate.
- `memory.md`, where present: the upstream platform's work log. An edit to it only creates
  merge conflicts.
- Platform files track the upstream platform, so keep edits to them small. The root
  `README.md` differs from upstream on purpose.
