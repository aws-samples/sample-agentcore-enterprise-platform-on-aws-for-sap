QUANTITY VARIANCE — INVOICE EXCEPTION RESOLUTION
STANDARD OPERATING PROCEDURE (SOP)
Version 1.6

================================================================================
PURPOSE
================================================================================

This SOP defines how the agent resolves a QUANTITY VARIANCE exception, where the
supplier invoice quantity differs from the goods receipt (GR) quantity in SAP
S/4HANA. It applies after three-way-match classification has identified the
exception as a quantity variance.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in RFC 2119.

================================================================================
SCOPE
================================================================================

Process Type: quantity_variance
SAP Modules:  MM (Materials Management), FI-AP (Accounts Payable)
SAP Service:  API_SUPPLIERINVOICE_PROCESS_SRV
Entities:     A_SupplierInvoice, A_PurchaseOrderItem, A_MaterialDocumentItem

================================================================================
PRECONDITIONS
================================================================================

Before execution, the following MUST be true:

1. The SAP MCP Server is reachable for reads and function imports.
2. The case payload contains the supplier invoice number and fiscal year.
3. The agent MUST NOT treat an earlier run of this case as a source of fact.
   Conversation history from earlier runs of the same case MAY be restored (it
   is kept for 30 days), but tool results are not, so every value the agent
   compares or writes MUST be read from SAP in this run.

================================================================================
STEP 1: GATHER DATA
================================================================================

1.1  The agent MUST retrieve the invoice line quantity (A_SupplierInvoice) and
     the PO reference.
1.2  The agent MUST retrieve the goods receipt quantity from the material
     document item (A_MaterialDocumentItem, filtered by PurchaseOrder/
     PurchaseOrderItem) for the same PO line. A_MaterialDocumentHeader carries
     no PurchaseOrder reference or quantity field.
1.3  The agent MUST NOT fabricate a GR quantity. IF no GR exists and the PO
     item's GoodsReceiptIsExpected is true, the agent MUST route the case as a
     missing_goods_receipt exception instead, even when the item's
     InvoiceIsGoodsReceiptBased is false.

================================================================================
STEP 2: CALCULATE VARIANCE
================================================================================

2.1  The agent MUST compute the quantity variance using the calculator tool:
       qty_variance_pct   = |invoice_qty - gr_qty| / gr_qty × 100
       qty_variance_units = |invoice_qty - gr_qty|
2.2  Both limits MUST be breached for the variance to be ABOVE tolerance:
       ABOVE  tolerance = qty_variance_pct > {{QTY_VARIANCE_PCT}}%
                          AND qty_variance_units > {{QTY_VARIANCE_UNITS}} units
       WITHIN tolerance = anything else
     Breaching only one limit is WITHIN tolerance. A small order breaching the
     percentage on a handful of units, and a large order breaching the unit
     count at a fraction of a percent, are both immaterial; escalating either
     is noise. Exceeding both is the signal. Clause 2.3 overrides this.
2.3  Whatever clause 2.2 returns, the agent MUST treat the item as ABOVE
     tolerance when the invoice bills more than ${{LINE_AMOUNT_TOLERANCE_USD}}
     above the quantity the goods receipt supports, which is the over-invoiced
     quantity multiplied by the purchase-order unit price. A unit count is not a
     dollar amount — {{QTY_VARIANCE_UNITS}} units is immaterial on a cheap part
     and thousands of dollars on an expensive one, and this clause is what
     removes that dependence on price.
2.4  The agent MUST NOT apply clause 2.3 when invoice_qty is less than gr_qty,
     because an under-billed invoice bills nothing extra and the amount clause
     2.3 measures is therefore zero.
2.5  The agent MUST NOT apply clause 2.3 when the invoice currency is anything
     other than USD, because that limit is denominated in US dollars, as its
     symbol name states, while the purchase-order unit price it multiplies is in
     the document's own currency. The invoice currency is the case attribute
     `currency`, taken from the invoice's DocumentCurrency. Where this clause
     applies, the agent MUST escalate the item to {{CONTACT_AP_TEAM}} for manual
     review, naming the currency and stating that this SOP declares no dollar
     limit for it, rather than deciding tolerance on the unit test in clause 2.2
     alone. The agent MUST NOT convert the amount into USD in order to apply
     clause 2.3, because this SOP declares no exchange rate and a rate the agent
     chose for itself would settle a material variance on an assumption nobody
     approved.

================================================================================
STEP 3: APPLY RESOLUTION LOGIC
================================================================================

3.1  IF the variance is WITHIN tolerance:
     - The agent MUST auto-accept and proceed to post the invoice (STEP 4).
     - The agent MUST also compare the PO item's OrderQuantity against the
       cumulative quantity received and invoiced to date. Matching the
       invoice to the GR is not the same as the PO being fully delivered —
       carry that distinction into STEP 5.

3.2  IF the variance is ABOVE tolerance AND invoice_qty < gr_qty (under-billing):
     - The agent MUST auto-accept the lower invoiced quantity and proceed to
       post (STEP 4). Under-delivery does not require approval.

3.3  IF the variance is ABOVE tolerance AND invoice_qty > gr_qty (over-billing):
     - The agent MUST raise an approval ticket to {{CONTACT_PROCUREMENT}} with
       PO#, invoice#, quantity difference, and $ impact.
     - The request MUST be an approval ticket, never a free-text one, because
       a free-text answer carries no decision the approval ceiling accepts.
     - On that ticket, Approve is the answer "approve as billed".
     - A Deny whose comment asks to pay only what the purchase order and goods
       receipt support is the answer "short pay". Any other Deny is "denied".
     - The request MUST name both answers the approver has: approve the invoice
       as billed, or SHORT PAY it — accept only the quantity the goods receipt
       supports and dispute the rest. Offering approval alone leaves a supplier's
       supported quantity unpaid for as long as the over-billing is argued over,
       which is the outcome this clause used to force.
     - The agent MUST record the disputed amount, its currency, and the reason in
       case state before stopping, because the SOP that executes a short pay
       reads them from there and MUST NOT recompute them.
     - The agent MUST update case state to "awaiting_human_input" and STOP.
     - IF approved as billed → proceed to post (STEP 4).
     - IF short pay → the agent MUST call `load_sop` with process_type
       `short_pay` and follow that SOP in place of STEP 4.
     - IF denied → the agent MUST mark the case for manual review by
       {{CONTACT_AP_TEAM}}.

================================================================================
STEP 4: EXECUTE RESOLUTION
================================================================================

4.0  The agent MUST NOT call Release or Post until the duplicate check in
     invoice_matching clauses 1.3 and 4.0 has been made in this run; IF that
     SOP is not in this run's prompt, the agent MUST load it with `load_sop`
     to read the check.

4.1  The agent MUST NOT attempt to park the invoice — the service exposes no
     Park function import. Once any required approval is confirmed, the agent
     MUST clear a blocked invoice with the Release function import, or post an
     invoice parked upstream with the Post function import.
4.2  The agent MUST update case state after each SAP write.
4.3  IF a write fails, the agent MUST set the case to 'error', notify
     {{CONTACT_AP_TEAM}} with the error, and STOP.

================================================================================
STEP 5: CLOSE CASE
================================================================================

5.1  The agent MUST update case status to 'complete' once the invoice is posted.
5.2  The agent SHOULD send a summary to {{CONTACT_AP_TEAM}}.
5.3  IF the PO item's OrderQuantity exceeds the cumulative quantity received
     and invoiced to date (or IsCompletelyDelivered / IsFinallyInvoiced is
     false), the case notes and the summary notification MUST state the open
     quantity and dollar amount remaining on the PO. A 0%-variance match
     against a partial goods receipt MUST NOT be reported as a fully closed
     PO.

================================================================================
ESCALATION RULES
================================================================================

| Trigger                              | Action                               |
|--------------------------------------|--------------------------------------|
| Over-billing above tolerance         | Approval ticket, {{CONTACT_PROCUREMENT}}|
| Approver chooses to short pay        | Route as short_pay                   |
| Approval denied                      | Manual review by {{CONTACT_AP_TEAM}} |
| No goods receipt found               | Route as missing_goods_receipt       |

CONTACTS
================================================================================

- AP Team:     {{CONTACT_AP_TEAM}}
