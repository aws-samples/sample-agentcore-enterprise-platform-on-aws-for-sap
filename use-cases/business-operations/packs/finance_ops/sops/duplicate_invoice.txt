DUPLICATE INVOICE — EXCEPTION RESOLUTION
STANDARD OPERATING PROCEDURE (SOP)
Version 1.4

================================================================================
PURPOSE
================================================================================

This SOP defines how the agent resolves a DUPLICATE INVOICE exception, where a
supplier invoice number already exists for the same vendor in SAP S/4HANA. It
applies after three-way-match classification has identified the exception as a
potential duplicate. The goal is to prevent double payment while not rejecting
legitimate resubmissions or corrective invoices.

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in RFC 2119.

================================================================================
SCOPE
================================================================================

Process Type: duplicate_invoice
SAP Modules:  FI-AP (Accounts Payable)
SAP Service:  API_SUPPLIERINVOICE_PROCESS_SRV
Entities:     A_SupplierInvoice

================================================================================
PRECONDITIONS
================================================================================

Before execution, the following MUST be true:

1. The SAP MCP Server is reachable for reads.
2. The case payload contains the supplier invoice number, vendor, and fiscal
   year.
3. The agent MUST NOT treat an earlier run of this case as a source of fact.
   Conversation history from earlier runs of the same case MAY be restored (it
   is kept for 30 days), but tool results are not, so every value the agent
   compares or writes MUST be read from SAP in this run.

================================================================================
STEP 1: GATHER DATA
================================================================================

1.1  The agent MUST retrieve the incoming invoice header (A_SupplierInvoice):
     vendor, invoice number, amount, currency, invoice date, and line items.
1.2  The agent MUST locate the suspected original with the read below, which
     is the same read invoice_matching clause 1.3 makes.
     - The agent MUST read A_SupplierInvoice with the filter
       `InvoicingParty eq '<InvoicingParty>' and SupplierInvoiceIDByInvcgParty
       eq '<SupplierInvoiceIDByInvcgParty>' and ReverseDocument eq ''`, taking
       both values from this invoice's own header, and selecting
       SupplierInvoice, FiscalYear, InvoiceGrossAmount, DocumentCurrency,
       DocumentDate, PostingDate, SupplierInvoiceStatus, PaymentBlockingReason
       and ReverseDocument.
     - `ReverseDocument eq ''` excludes reversed invoices and reversal
       documents, which share the original's reference but are not a second
       claim for payment.
     - IF this invoice's SupplierInvoiceIDByInvcgParty is empty, the agent MUST
       replace that term with `InvoiceGrossAmount ge <low>M and
       InvoiceGrossAmount le <high>M`, where low and high are this invoice's
       InvoiceGrossAmount minus and plus ${{DUPLICATE_MATCH_WINDOW_USD}},
       computed with the calculator tool.
     - A single quote inside a filter value MUST be doubled (`O''Brien`), as
       OData string literals require.
     - The agent MUST NOT filter on SupplierInvoice for this check, because SAP
       assigns that number fresh on every posting and a duplicate never shares
       it.
1.3  IF the STEP 1.2 query returns no earlier invoice for that invoicing party
     and invoice reference, the duplicate premise does not hold and there is
     nothing to compare against. The agent MUST NOT treat an unmatched invoice as
     a duplicate. The agent MUST reprocess the invoice through three-way matching
     and follow that SOP's resolution logic in place of STEP 2 and STEP 3.

================================================================================
STEP 2: COMPARE AGAINST THE ORIGINAL
================================================================================

2.1  The agent MUST compare the incoming invoice with the existing one on:
     amount, invoice date, and line items.
2.2  The agent MUST compute the amount difference using the calculator tool:
       amount_difference = |incoming_amount - original_amount|

2.3  The agent MUST NOT measure the amount difference against
     ${{DUPLICATE_MATCH_WINDOW_USD}} when the two invoices are denominated in
     different currencies, or when either is denominated in anything other than
     USD, because that window is denominated in US dollars, as its symbol name
     states. An invoice's currency is the case attribute `currency`, taken from
     its DocumentCurrency. Where this clause applies, the agent MUST escalate to
     {{CONTACT_AP_TEAM}} for manual review under clause 3.2, naming both
     currencies, rather than resolving the case under clause 3.1. The agent MUST
     NOT convert either amount in order to compare them, because this SOP declares
     no exchange rate and a rate the agent chose for itself would decide whether
     an invoice is paid twice on an assumption nobody approved.

================================================================================
STEP 3: APPLY RESOLUTION LOGIC
================================================================================

3.1  IF the incoming invoice matches the original on amount (within
     ${{DUPLICATE_MATCH_WINDOW_USD}}), date, and line items:
     - The agent MUST treat it as a TRUE DUPLICATE. The agent MUST NOT post it.
     - The agent MUST reject the invoice and notify the vendor via
       {{CONTACT_AP_TEAM}}, referencing the original invoice/document number.
     - The agent MUST update case state to 'complete' with disposition
       "rejected_duplicate".

3.2  IF the amount difference exceeds ${{DUPLICATE_MATCH_WINDOW_USD}} OR line items
     differ:
     - The invoice MAY be a partial, corrective, or resubmitted invoice. The
       agent MUST raise an approval ticket to {{CONTACT_AP_TEAM}} with both
       invoices' numbers, amounts, dates, and the differences identified.
     - The agent MUST create that ticket with category "duplicate_review",
       because invoice_matching clause 4.0a recognises the resumed run by that
       category and by nothing else.
     - The ticket MUST name every original invoice number the duplicate read
       returned, because invoice_matching clause 4.0a checks the resumed run
       against those numbers.
     - The agent MUST NOT use category "duplicate_review" on any other ticket.
     - On that ticket, Approve is the answer "post it as a separate invoice",
       and Deny is the answer "reject it".
     - The agent MUST update case state to "awaiting_human_input" and STOP.
     - IF approved, the agent MUST clear the invoice's block with the verb
       invoice_matching clause 4.1 selects; clause 4.0a of that SOP exempts
       this run from the duplicate gate.
     - IF denied, the agent MUST reject the invoice as in clause 3.1.

3.3  The agent cannot read payment status — the service exposes
     SupplierInvoiceStatus and PaymentBlockingReason, not a cleared/paid flag.
     Where the original is posted and carries no payment block, the agent MUST
     treat double payment as possible, say so explicitly in the notification to
     {{CONTACT_FINANCE_APPROVALS}}, and state that payment status needs human
     confirmation. The agent MUST NOT assert that the original was or was not
     paid.

3.4  The agent MUST NOT post a suspected duplicate without human confirmation.

================================================================================
STEP 4: CLOSE CASE
================================================================================

4.1  For a confirmed true duplicate, the agent MUST close the case with the
     rejection recorded.
4.2  For an escalated corrective/partial invoice, the agent MUST wait for the AP
     team's decision before any posting, then act on it under clause 3.2.
4.3  IF a write fails, the agent MUST set the case to 'error', notify
     {{CONTACT_AP_TEAM}}, and STOP.

================================================================================
ESCALATION RULES
================================================================================

| Trigger                                   | Action                              |
|-------------------------------------------|-------------------------------------|
| True duplicate                            | Reject + notify {{CONTACT_AP_TEAM}} |
| Amount/line-item difference               | Approval ticket, {{CONTACT_AP_TEAM}}|
| Original already paid (double-pay risk)   | Flag {{CONTACT_FINANCE_APPROVALS}}  |
